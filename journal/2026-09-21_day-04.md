### Part 1: Servo code rewrite (`src/servo_sorter.py`, +35 / −52 lines)

#### 1a. 4 bins → 2 bins
**Mentor's:**
```python
BIN_ROTATE_ANGLES = {"glass": 0, "metal": 60, "plastic": 120, "other": 180}
```
**Mine:**
```python
ROTATE_CHANNEL = 8
ROTATE_NEUTRAL_ANGLE = 90      # platform centered
ROTATE_RECYCLE_ANGLE = 0       # Recycle side under the drop
ROTATE_TRASH_ANGLE = 180       # Trash side under the drop

BIN_ROTATE_ANGLES = {
    "Recycle": ROTATE_RECYCLE_ANGLE,
    "Trash": ROTATE_TRASH_ANGLE,
}
```
- This matches the `"Recycle"` / `"Trash"` names from `category_map.py` (Day 2).
- Anything unexpected goes to Trash: `BIN_ROTATE_ANGLES.get(category, ROTATE_TRASH_ANGLE)`.

#### 1b. Raw, measured angles instead of offset math
**Mentor's** tilt used "logical" angles plus a conversion:
```python
TILT_OFFSET = 60
TILT_NEUTRAL_ANGLE = 90        # logical → 90 − 60 = 30° real
TILT_DROP_ANGLE = 150          # logical → 150 − 60 = 90° real

def _set_tilt(self, logical_angle):
    physical_angle = max(0, min(180, logical_angle - TILT_OFFSET))
```
**Mine:** real angles I measured with `scripts/calibrate_servo.py`, no math:
```python
TILT_CHANNEL = 11
TILT_NEUTRAL_ANGLE = 30        # tray is flat
TILT_DROP_ANGLE = 120          # tray tipped far enough to drop the item
```
- **Why:** with the offset, the number in the code (150) wasn't the number the servo actually went to (90). That made tuning confusing. Now what you see is what the servo does.
- My comment in the file: *"All angles below are RAW values sent directly to the servo - no offset or conversion math. Re-run the manual calibration one-liner and update these five numbers if the physical build changes."*

#### 1c. Tilt angle: items weren't falling off
- **Problem:** light items (paper, wrappers) stayed on the tray at the original drop angle. Gravity on a light item wasn't enough to beat friction.
- **Fix:** I tested bigger angles until items reliably fell: **75° → 90° → 120°**. 120° worked.
- **Source:** chat log, Sep 21. The final value 120 is confirmed in the saved file. The mentor's code effectively dropped at 90° real.

#### 1d. Servos always return to the start position
**Mentor's:** the reset steps ran only if nothing went wrong in the steps before them.
**Mine:** wrapped in `try / finally`, so the reset **always** runs, even if an error happens mid-sort:
```python
try:
    self._kit.servo[ROTATE_CHANNEL].angle = rotate_angle    # 1. rotate to the bin
    time.sleep(1.0)
    self._kit.servo[TILT_CHANNEL].angle = TILT_DROP_ANGLE   # 2. tip to 120°
    time.sleep(1.3)
finally:
    self._kit.servo[TILT_CHANNEL].angle = TILT_NEUTRAL_ANGLE    # 3. ALWAYS flatten the tray
    time.sleep(0.4)
    self._kit.servo[ROTATE_CHANNEL].angle = ROTATE_NEUTRAL_ANGLE  # 4. ALWAYS re-center
    time.sleep(0.8)
```
- **Why it matters:** during debugging, an intermediate version of my code reset the tilt but **not** the rotate servo, so the platform stayed turned to one side (chat log, Sep 21). If the platform isn't back at center, the camera's "empty tray" picture is wrong, and the next sort goes wrong too.
- **Timing:** one full sort takes 1.0 + 1.3 + 0.4 + 0.8 = **3.5 seconds**.

#### 1e. Clear error messages
**Mentor's:** if the servo board wasn't found, it quietly switched to "pretend" mode:
```python
except (ImportError, NotImplementedError, ValueError):
    self._kit = None
```
**Mine:** it says so loudly, with the exact reason:
```python
    print("[servo sorter] Hardware initialized successfully.")
except Exception as e:
    print(f"[servo sorter] !! Failed to initialize hardware: {type(e).__name__}: {e}")
    self._kit = None
```
- **Why:** when the servos weren't moving, I couldn't tell whether the code was in "pretend" mode or the hardware had failed. Now the first line printed tells me.

### Part 3: Shutdown button

Pulling the power on a Raspberry Pi can **corrupt the SD card**, and the bin has no keyboard. So I added a button: **hold it for 2 seconds → the Pi shuts down safely.**

#### 3a. `button_monitor.py` (12:53 PM): testing the wiring
Prints only when the button **changes** (pressed ↔ released), so it's easy to watch:
```python
GPIO_PIN = 12
...
if pressed != last_state:
    print("[monitor] PRESSED" if pressed else "[monitor] RELEASED")
    last_state = pressed
time.sleep(0.05)        # check 20 times per second
```
- This one watches **GPIO12**. The final button is on **GPIO21** (tested with `test_button.py` on Day 2). **(Reconstructed)** I most likely tried pin 12 first before settling on 21.

#### 3b. `shutdown_button.py` (1:05 PM): the real thing
```python
"""Holds GPIO21 low (button pressed, wired to GND) for 2 seconds -> safely
shuts down the Pi. Talks to the GPIO pin directly via lgpio instead of
gpiozero, since gpiozero's automatic pin-driver detection isn't working
correctly on this system."""
import time, subprocess, lgpio

GPIO_PIN = 21           # physical pin 40
HOLD_SECONDS = 2.0

h = lgpio.gpiochip_open(0)
lgpio.gpio_claim_input(h, GPIO_PIN, lgpio.SET_PULL_UP)

held_since = None
try:
    while True:
        pressed = (lgpio.gpio_read(h, GPIO_PIN) == 0)     # active low
        if pressed:
            if held_since is None:
                held_since = time.time()                    # start the timer
            elif time.time() - held_since >= HOLD_SECONDS:  # held 2 s?
                subprocess.run(["sudo", "shutdown", "-h", "now"])
                break
        else:
            held_since = None                               # let go → reset timer
        time.sleep(0.05)
finally:
    lgpio.gpiochip_close(h)
```
**How it works:**
1. Check the button **20 times per second**.
2. When it's first pressed, remember the time.
3. If it's **still** pressed 2 seconds later → run `sudo shutdown -h now` (safe shutdown).
4. If it's released early, reset the timer. A quick bump **doesn't** shut anything down.

**Why `lgpio` instead of `gpiozero`:** `gpiozero` is the usual easy library, but its automatic pin-driver detection didn't work on my Pi (written in my comment at the top of the file). `lgpio` talks to the GPIO chip directly.

#### 3c. Making it start automatically (systemd service)
File: `/etc/systemd/system/shutdown-button.service`
```ini
[Unit]
Description=GPIO Shutdown Button
After=multi-user.target

[Service]
WorkingDirectory=/home/kevinwei0117/raspi-ai-trashcan
ExecStart=/usr/bin/python3 /home/kevinwei0117/raspi-ai-trashcan/shutdown_button.py
Restart=always
RestartSec=3
User=kevinwei0117

[Install]
WantedBy=multi-user.target
```
- **systemd** is the Pi's built-in manager for background programs.
- `After=multi-user.target`: start once the Pi has finished booting.
- `Restart=always` + `RestartSec=3`: if the script ever crashes, restart it after 3 seconds.
- Turned it on with:
  ```bash
  sudo systemctl enable shutdown-button.service     # start at every boot
  sudo systemctl restart shutdown-button.service    # start it now
  sudo systemctl status shutdown-button.service     # check it's running
  ```
- **(Reconstructed)** I don't know the exact time of day I created the service file, only that it's been confirmed working.

### What I learned
1. **Measure, don't guess:** the starting angles were estimates. The calibration tool gave me the real numbers.
2. **`try / finally`** guarantees cleanup code runs, which is important for anything that moves.
3. **Loud error messages save time.** Silent "pretend mode" hid real hardware problems.
4. **Only one program can use the camera at a time.** Check for leftover background copies (`ps aux | grep`).
5. **Motors need their own power** and solid connections. Most "random" servo problems are power problems.
6. **Background services (systemd)** let a script start by itself every time the Pi boots.
